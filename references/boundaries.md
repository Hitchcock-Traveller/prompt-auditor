# 边界、反例与失败模式

> 框架是免费的，边界才值钱。
> 这一份是本 skill 的核心资产——中文传播里普遍被删掉的部分。

---

## 一、每档的边界

| 维度 | 依据 | 边界 | 反例 |
|---|---|---|---|
| **高度** | 修闪退 → 让 App 不再闪退，解空间扩大 | 目标过宽易泛化失效 | 笼统说「做个好产品」反而无解 |
| **深度** | 给行业趋势后分析更有洞察 | 信息越多不一定越好，噪声会干扰 | 塞入无关数据反而稀释重点 |
| **广度** | 「做 PPT」→「让忙人看懂并决策」，触发信息取舍 | 过度跨界会偏离原任务 | 让 AI「像诗人一样写报告」损害专业性 |

**一句话概括**：三维法不是"越高越好"，是**找到那个刚好还能落地的最高点**。每往上拉一档，都要问一句"拉到这还能不能验收"。

## 二、六种不该升级的情形

这是本 skill 的第一道闸门。命中任意一条，**直接告诉用户不需要升级**。

### 1. 封闭任务，有唯一正确答案

写正则、改错别字、格式转换、单位换算、时间格式规范化。

**理由**：这类任务的解空间本来就只有一种正确答案，拉高目标只会让模型在无关维度上发挥。你要的是「把 2026/11/9 转成 2026-11-09」，不是「让这个日期对读者产生意义」。

### 2. 一次性事实查询

「XX 是什么时候发布的」「这个 API 的参数有几个」。

**理由**：事实查询的瓶颈在信息源，不在提问方式。拉高只会让模型多说废话。

### 3. 用户自己无法验证结果

用户不懂该领域，拉高后给出的答案他也判断不了对错。

**理由**：这是最危险的一类。Depth 档要求"用顶尖的方法做完"，但用户不知道顶尖方法长什么样，模型给的答案看起来专业、实际可能是编的。**这时候拉高不是提升质量，是提升欺骗性。**

**正确做法**：建议用户先补领域基础，或者把任务降级为"给我三个候选方案 + 各自的判据"，让他能做选择而不是做评估。

### 4. 时间或成本敏感

明确要求快速出结果，或者按 token 计费跑量。

**理由**：每升一档，模型的推理轮次和输出长度都会显著增加。批量任务上拉高深度，成本可能翻几倍。

### 5. 输出规格已完全确定

接口要求的固定 JSON 结构、固定字数、固定模板、固定字段。

**理由**：规格已经锁死，拉高只会让模型在格式上犯错。

### 6. 目标已经空到无法验收

已经是「做个好产品」「写篇好文章」这种级别。

**理由**：这时候需要的是**降低抽象层级**，不是继续拉高。先问"你说的好，具体是指什么"，把它变成可验收的标准，再考虑往上拉。

## 三、失败模式分类

按"拉高之后坏在哪"分类，用于诊断。

### 失败模式 A：拉空了（泛化失效）

**症状**：目标很宏大，但模型给出的东西无法判断对错，也无法直接使用。

**典型**：把「帮我写个爬虫」改成「帮我建立一个数据获取体系」。

**根因**：上溯目标时，跳过了「可验收」这一层。目标是高了，但没有落地锚点。

**修法**：补一句验收标准。不能补，说明这个目标还没想清楚。

### 失败模式 B：噪声稀释

**症状**：给了大量背景材料，输出反而不如只给关键信息。

**典型**：为了"深度"，把十篇论文全文塞进去，结果模型抓错了重点。

**根因**：混淆了"更多信息"和"更原始信息"。**原始 ≠ 更多**。一份原始日志比十份二手总结有用；但三份不相关的原始日志，比一份关键日志更糟。

**修法**：按"这份材料能不能直接改变结论"筛选，不能的删掉。

### 失败模式 C：跨界跑偏

**症状**：借了别的领域的做法，但丢了原任务的核心约束。

**典型**：「像诗人一样写技术报告」——文采有了，技术准确性没了。

**根因**：借的是**形式**，不是**流程**。

**修法**：明确哪些约束不能动（数据准确性、术语规范、结论可验证），再借方法。

### 失败模式 D：范围越界

**症状**：模型做了你没要求的事，而且做得挺对，但你不能接受。

**典型**：让它改一个函数，它顺手重构了整个模块，还删了一个看似冗余的公开接口。

**根因**：拉高目标时没划定边界。**做得更多不等于做得对。**

**修法**：在 prompt 里明确"不要动什么"。这条比"要做什么"更容易被忽略，但在真实工程里更致命。

### 失败模式 E：自我评分偏松

**症状**：模型自己检查自己的输出，结论永远是"看起来不错"。

**根因**：结构性问题，不是能力问题。

**修法**：换一个独立会话做验证，或者给出可执行的检查清单让它逐项打勾。

## 四、三个流派的比较

| 方法 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|
| **Few-shot 示例法** | 稳定性高，输出可控 | 灵活性低，换个任务就得重写样例 | 格式固定、风格要求明确的批量任务 |
| **专家角色法** | 简单，一句话 | 容易止步于措辞，模型换了词没换方法 | 需要特定语气、特定视角的表达任务 |
| **四档法（本框架）** | 表达力强，能处理开放任务 | **依赖用户领域知识，门槛最高** | 开放式、需要判断力的复杂任务 |

**门槛最高这一条要留着，不能藏。**

四档法的前提是"你知道顶尖的人怎么做"——这恰恰是新手最缺的。所以它更适合**已经在某个领域有判断力的人**，不适合完全的新手。

新手用四档法，容易出现"看起来拉高了，实际上拉空了"——让 AI"用顶尖数据科学家会用的方法"，但自己不知道那是什么，模型给的答案也验不了。

## 五、组合使用

三种方法不是互斥的。实践中常见的组合：

**Depth + Few-shot**：先用四档法定方向，再用 few-shot 锁格式。适合需要既深又规整的输出。

**Range + 专家角色**：用 Range 找跨领域的方法框架，用专家角色调语气。适合对外交付的文档。

**Altitude + 独立验证**：拉高目标之后，必须配一个独立的验收环节。这是唯一不能省的组合。
